# Squash 汇总到 main 后推送云端

用户明确发起“推送云端”等命令时，已授权本次任务 squash 到本地 main 并推送 main，不重复询问。开发分支确认和自动本地 commit 本身不授权合并或推送。仅授权本地合并时执行到汇总提交及验证，保留原分支，不推送或进入交付后归档。默认开发分支为 `codex/dev`，其原始提交与归档仅在本地保留。

1. 确定本次任务、开发分支、tip SHA 和全部待交付提交，按用户指定或唯一可判定配置选择远端；多个候选不猜测。检查 `git worktree list` 与工作区状态。main 已被检出时使用其干净工作目录；有无关改动或被其他任务使用时停止说明，不强制切换、reset、stash 或清理用户文件。必要时使用安全的隔离 worktree。
2. Fetch 选定远端并核实 main：只有远端 main 时可基于它建立本地 main；两者均不存在时停止。没有可比较的远端 main 时，不擅自创建远端分支。核查本地 main 领先提交与开发分支待合入提交，只纳入本次已确认任务；未知或无关提交须先解决范围问题，不能以 squash 掩盖它们。
3. 先同步远端 main：可快进时快进；已分叉时仅在两侧提交归属及授权均明确、无冲突时正常 merge 保留历史，否则报告阻塞。记录同步后的 main SHA 为 `integration_base_sha`，固定本次源分支 tip 与提交清单。尚未开始整合的新批次按下一步 squash；若本批次已生成汇总提交，按记录恢复，不重复 squash。
4. 在干净的本地 main 上对已核实 tip 执行 `git merge --squash <任务tip-SHA>`。即使可以快进，任务交付仍使用 squash，使整个已确认批次在 main 上只新增一条汇总提交。若本次明确涵盖多个开发分支，先核清各分支归属和依赖，在同一次整合中汇集全部已授权改动后生成一条汇总提交；不能把“全部”扩展到仓库其他分支。出现冲突时保留现场并报告，不强行解决业务歧义。
5. 审查实际 staged diff 是否完整覆盖本次最终改动，并运行受整合影响的测试/构建；失败或关键验收无法验证时不创建完成提交、不推送。按 [提交规范](commits.md) 撰写中文 Conventional Commits 汇总消息，以 `feat:`、`fix:`、`refactor:` 等概括目标，正文适度归纳全部主要成果，不采用逐条 commit 列表。用 `git commit -F <消息文件>` 正常提交；不 amend/rebase 原始开发提交或既有 main 历史。没有净改动时不创建空提交，核查是否已交付并记录真实状态。
6. 核实汇总提交 SHA、消息和实际内容，记录 `integration_method=squash`、来源分支/tip/原始提交、整合基点、汇总 SHA 与检查结果。检查最终 main 与已验证内容一致；提交 hook 或后续修改改变了内容时补做相关验证。仅获准本地合并时在此交付“已 squash 合入 main，未推送”。
7. 再核查相对远端 main 的全部待推送提交，只推明确授权范围。使用明确 refspec：`git -c push.followTags=false push --no-follow-tags <已确认远端> refs/heads/main:refs/heads/main`。不使用裸 push、`--all`、`--mirror`、force push，也不直接从开发分支映射到远端 main；不连带推送归档分支或标签。
8. 查询或重新 fetch 远端 main，确认其包含本次 **main 汇总提交 SHA**；例如对已核实的远端 main 引用执行 `git merge-base --is-ancestor <汇总SHA> <远端main引用>`。不检查原始开发提交是否为远端 main 的祖先，squash 不建立这种父子关系。远端竞态导致拒绝时重新 fetch、核对范围，在授权范围内安全同步已生成的 main 汇总提交并重验；不再次 squash、不强推、不盲目反复推送。记录汇总 SHA 与实际已推送 main SHA，失败时保留现场。

## 交付后的本地归档与下一轮开发

本次完整 squash 结果验证通过，且远端 main 已确认包含汇总提交后，默认自动将本任务的本地 `codex/` 开发分支改名归档，无需再次询问。归档保留详细开发历史并腾出 `codex/dev` 名称；它替代旧的自动删除规则。仅本地合并、部分交付或推送失败时保留原分支。

- 归档前核实整个分支 tip 对应的本次改动均已交付，tip 仍与整合记录一致；分支后来新增了提交时不归档。保存原分支名、tip SHA、原始提交清单和对应汇总 SHA。只核验内容覆盖与已记录的整合结果，不把原始 tip 是 main 的祖先作为 squash 成功条件。
- 检查所有 worktree 及其归属。仅在本任务干净且未被其他任务使用的工作目录操作；有未提交改动、重要未跟踪/忽略文件、其他任务占用或归属不明时保留并报告。分支正在本任务 worktree 检出时，可在该目录安全改名，保留文件和 worktree，遵守 managed-worktree 的管理约定。
- 使用不覆盖已有引用的 `git branch -m <原分支> archive/codex-dev-<task-id>`；若一批有多个源分支，在归档名中加入各自分支标识以避免重名。目标已存在时核实记录，不使用 `-M` 覆盖。归档后核实新引用与原 tip 相同、原分支名已腾出。不得用 `git branch -D` 绕过 squash 后的删除限制，不删除归档、其他任务分支或远端分支，也不把归档推送到远端。
- 记录 `branch_cleanup` 的原分支、tip、归档名、汇总 SHA、时间与结果/保留原因。分别报告本地提交、squash 合入 main、main 推送、归档和部署，归档失败不伪装成推送失败。
- 下一轮先检查 `codex/dev` 是否存在：存在则按 SKILL.md 的默认复用规则核对并继续使用，优先复用其工作目录；只有不存在时才从已核实的最新 main 创建同名分支。新需求、新任务或新聊天不触发额外分支或提前归档；不在已归档的旧开发历史上继续积累提交。无法安全复用时先说明阻塞，不自动重置旧分支或另建替代分支。
