# Squash 汇总到 main 后推送云端

用户明确发起“推送云端”等命令时，已授权本次任务 squash 到本地 main 并推送 main，不重复询问。开发分支确认和自动本地 commit 本身不授权合并或推送。仅授权本地合并时执行到汇总提交、验证及安全删除开发分支，不据此推送。默认开发分支为 `codex/dev`，仅本地使用；完整合入 main 后删除，不再改名归档。

1. 确定本次任务、开发分支、tip SHA 和全部待交付提交，按用户指定或唯一可判定配置选择远端；多个候选不猜测。检查 `git worktree list` 与工作区状态。main 已被检出时使用其干净工作目录；有无关改动或被其他任务使用时停止说明，不强制切换、reset、stash 或清理用户文件。必要时使用安全的隔离 worktree。
2. Fetch 选定远端并核实 main：只有远端 main 时可基于它建立本地 main；两者均不存在时停止。没有可比较的远端 main 时，不擅自创建远端分支。核查本地 main 领先提交与开发分支待合入提交，只纳入本次已确认任务；未知或无关提交须先解决范围问题，不能以 squash 掩盖它们。
3. 先同步远端 main：可快进时快进；已分叉时仅在两侧提交归属及授权均明确、无冲突时正常 merge 保留历史，否则报告阻塞。记录同步后的 main SHA 为 `integration_base_sha`，固定本次源分支 tip 与提交清单。尚未开始整合的新批次按下一步 squash；若本批次已生成汇总提交，按记录恢复，不重复 squash。
4. 在干净的本地 main 上对已核实 tip 执行 `git merge --squash <任务tip-SHA>`。即使可以快进，任务交付仍使用 squash，使整个已确认批次在 main 上只新增一条汇总提交。若本次明确涵盖多个开发分支，先核清各分支归属和依赖，在同一次整合中汇集全部已授权改动后生成一条汇总提交；不能把“全部”扩展到仓库其他分支。出现冲突时保留现场并报告，不强行解决业务歧义。
5. 审查实际 staged diff 是否完整覆盖本次最终改动，并运行受整合影响的测试/构建；失败或关键验收无法验证时不创建完成提交、不推送。按 [提交规范](commits.md) 撰写中文 Conventional Commits 汇总消息，标题、正文及必要 footer 合计不超过 100 字，提交前计数。优先一句话概括核心成果，保留必要的破坏性变更说明，详细清单与验证过程留在任务记录。用 `git commit -F <消息文件>` 正常提交；不 amend/rebase 原始开发提交或既有 main 历史。没有净改动时不创建空提交，核查是否已交付并记录真实状态。
6. 核实汇总提交 SHA、消息和实际内容，记录 `integration_method=squash`、来源分支/tip/原始提交、整合基点、汇总 SHA 与检查结果。检查最终 main 与已验证内容一致；提交 hook 或后续修改改变了内容时补做相关验证。按下文检查并删除已完整合入的本地开发分支；仅获准本地合并时在此交付“已 squash 合入 main，未推送”及分支清理结果。
7. 再核查相对远端 main 的全部待推送提交，只推明确授权范围。使用明确 refspec：`git -c push.followTags=false push --no-follow-tags <已确认远端> refs/heads/main:refs/heads/main`。不使用裸 push、`--all`、`--mirror`、force push，也不直接从开发分支映射到远端 main；不连带推送归档分支或标签。
8. 查询或重新 fetch 远端 main，确认其包含本次 **main 汇总提交 SHA**；例如对已核实的远端 main 引用执行 `git merge-base --is-ancestor <汇总SHA> <远端main引用>`。不检查原始开发提交是否为远端 main 的祖先，squash 不建立这种父子关系。远端竞态导致拒绝时重新 fetch、核对范围，在授权范围内安全同步已生成的 main 汇总提交并重验；不再次 squash、不强推、不盲目反复推送。记录汇总 SHA 与实际已推送 main SHA，失败时保留现场。

## 合入 main 后删除本地开发分支

整个源分支的最终改动已完整合入本地 main 并验证通过后，默认自动删除本任务的本地 `codex/` 开发分支，无需再次询问，不创建归档分支。仅本地合并也适用，不以推送成功为前提；推送失败时保留 main 上的汇总提交和任务记录，以便继续推送。未完整合入、验证未通过或存在未交付工作时保留分支。

- 删除前保存原分支名、tip SHA、原始提交清单和汇总 SHA；再次核实源 tip 与整合记录一致，且整个分支的最终改动均在当前 main 中有效保留。分支后来新增提交、只合入部分改动或内容覆盖不明确时不删除。不得仅以提交消息、远端已有同名分支或 main 包含一个汇总提交就认定全部改动已保留。
- 普通 merge 可用 `git merge-base --is-ancestor <源tip> main` 核验祖先关系。Squash 不建立这种关系：检查 main 包含已验证的汇总 SHA，并对照整合差异、源分支最终内容及检查记录确认完整覆盖。没有其他 main 改动时可用 `git diff --quiet <源tip> <汇总SHA>` 确认树一致；main 有独立改动或冲突解决时按实际受影响文件核对，不能把整树不同自动当成丢失，也不能跳过覆盖核验。
- 检查所有 worktree 及其归属。仅操作本任务干净且未被他人使用的工作目录；有未提交改动、重要未跟踪/忽略文件、其他任务占用或归属不明时保留并报告。源分支仍在本任务目录检出时，安全切到 main；main 已在另一 worktree 检出时，可在本任务目录 detach 到已验证的 main 提交。保留工作目录和文件，不强制切换、不自动清理 worktree。
- 确认源分支已不被任何 worktree 检出、tip 未变化且覆盖核验通过后，优先 `git branch -d <源分支>`。若仅因 squash 未建立祖先关系而被拒绝，且上述检查全部通过，可按本规则的删除授权使用 `git branch -D <源分支>`；其他失败原因先核实，不用 `-D` 绕过未合并内容、占用或未知状态。仅删除本任务已核实的本地开发分支，不批量删除旧归档、其他任务分支或远端引用。
- 删除后核实源分支不存在、main 汇总提交及内容仍在。记录 `branch_cleanup` 的 `action=delete`、原分支、tip、汇总 SHA、覆盖依据、时间与删除结果/保留原因。分别报告本地提交、合入 main、分支删除、main 推送和部署；清理失败不伪装成合并或推送失败。
- 下一轮先检查 `codex/dev` 是否存在：存在则核对并复用，优先使用其工作目录；只有不存在时才从已核实的最新 main 创建同名分支。新需求、新任务或新聊天不触发提前删除；无法安全复用时说明阻塞，不重置旧分支或另建替代分支。
