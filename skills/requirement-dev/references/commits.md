# 开发提交与交付汇总规范

依据 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。开发提交与 squash 后的 main 汇总提交均使用中文描述，默认省略 scope。开发时每完成一个已确认需求并验证通过，自动在本地开发分支（默认 `codex/dev`）提交；交付时将本次批次汇总为一条 main 提交。

格式：

```text
<type>[可选 scope][可选 !]: <中文描述>

[可选中文正文]

[可选 footer]
```

- 冒号与后续空格使用 `: `。type 使用英文小写：新功能 feat、修复 fix；按实际变更可用 docs、refactor、test、perf、build、ci、chore 等，不把所有改动一律标为 feat。
- 描述由需求和实际改动提炼，简短、具体、以中文表述；必要的 API、产品名或标识符可保留原名。不能只写“完成需求”“修改代码”，不能声称未实现的内容已完成。
- scope 默认省略。仅仓库工具强制要求，或确实需要明确模块归属时才使用，例如 `fix(auth): 修复登录状态过期后无法重新登录`；不为凑格式加括号。
- 开发阶段，一个需求内的代码、测试和必要文档可共用一个提交，以主要目的选 type；多个独立需求分别提交。main 上的 squash 汇总提交覆盖整个已确认交付批次。
- 实际存在破坏性变更时使用 `!` 或 `BREAKING CHANGE: 中文说明`，不得省略标记；不主动制造破坏性变更。必要正文与标题间留一空行，footer 也留一空行。
- 保留仓库已有 hook 和提交校验；与中文/省略 scope 的用户要求冲突且无法兼容时说明具体冲突，不擅自更改规则。

开发提交示例：

```text
feat: 增加用户列表邮箱搜索
fix: 修复清空筛选条件后列表未刷新
refactor: 合并订单状态转换逻辑
feat!: 移除旧版登录接口

BREAKING CHANGE: 客户端需迁移到新版登录接口
```

## Squash 汇总提交

- 阅读本次待合入开发分支的完整改动、需求记录和提交历史，以实际最终 diff 为准，总结所有已确认纳入本批次的成果；不遗漏重要改动，也不混入无关分支或未授权任务。
- 标题仍为 `<type>: <中文概括>`，按本次改动的主要目的选择 `feat`、`fix`、`refactor` 等类型，不能因为用了 squash 就一律写成 `chore: 合并分支`。
- 正文按功能或问题归纳主要改动，可用短段落或少量要点。覆盖关键行为变化、必要的兼容性说明与有实际意义的验证结论；以最终实现为主，不逐条复述、拼接 commit 标题，不罗列中间试错、返工或全部检查命令。
- 详略随本次改动规模调整，不固定字数或条数；简单改动无需凑正文，复杂改动不能只用笼统一句话。保留必要的破坏性变更标记，不宣称未完成或未验证的结果。
- 使用 `git merge --squash` 形成待提交改动，验证后以重新撰写的消息正常 `git commit`；不要直接采用 Git 生成的逐条提交列表，也不要将 `git commit --squash` 当成合并命令。

汇总示例：

```text
feat: 完善订单查询与导出功能

支持按状态、日期组合筛选及批量导出，统一列表与导出的数据口径。
修复筛选条件重置和空结果处理问题，补齐相关查询与导出验证。
```

通过结构化 Git 工具或安全传递消息文本来提交；多行消息优先写入临时文件后使用 `git commit -F`，避免把需求文本直接插入可执行 shell 字符串。
