# 验收报告规范

报告为 `report.md`，证据放同一运行目录的 `evidence/`，按需创建。运行目录遵循 SKILL.md 的项目内保存规则；报告与证据使用相对链接，便于在项目内查阅和迁移；运行目录按 SKILL.md 规则由 Git 忽略，不随代码提交。每次运行新建目录，不覆盖历史。下列是结构说明；输出时用真实数据填充，不保留空白模板，不虚构证据。

## 验收结论

总评：通过 / 未通过 / 待验收完成。

注明任务 ID、开发任务 ID（如有）、验收时间与时区、各需求来源的链接/绝对路径或会话来源、读取时间、版本或哈希、选中问题/章节、仓库路径、代码 SHA、未提交改动标识、运行 URL/环境/实际版本、与上轮报告的关联。

本地 MD 的章节、问题 ID 或行号需对应已保存快照；直接描述引用用户原话。多来源逐一列出，不要求用飞书 URL 填写本地文件来源。

说明测试依据和边界：确认范围、文档变更、未覆盖部分及其原因。统计本次范围内通过、未通过、阻塞、未验证的条目数量及总数，不能将未执行条目从分母移除来提高通过率。

## 逐项验收

| ID | 需求出处/条目 | 预期行为 | 验证方式与实际结果 | 状态 | 证据 |
|---|---|---|---|---|---|

证据引用应能追踪到具体命令输出、代码位置、请求结果或截图。代码引用使用实际文件和行号；日志记录命令、工作目录、退出码。截图记录访问环境、操作和观察结果，不写成证明所有场景通过。

## 问题列表

每个问题包含：
- 稳定问题 ID、关联验收 ID、影响程度（阻断/重要/一般）。
- 复现前提与步骤；预期和实际结果。
- 证据链接；涉及代码位置（已确定时）。
- 影响与建议修复方向，不把猜测原因写成已确认根因。

需求歧义与环境阻塞单独列出，说明恢复验证需要什么。不把无法登录等环境问题冒充产品缺陷。

## 检查与后续

列出实际执行的检查命令、结果、测试数据与清理情况；概述哪些验收项仅静态检查，哪些已运行验证。列出下一步修复或补验动作。不存在问题时明确写无已确认问题，不捏造风险填充版面。

如需交给开发者修复，提供问题 ID、需求出处、复现步骤、预期结果和证据；本报告本身不授权代码修改、推送或发布。
