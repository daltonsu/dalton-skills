# fork项目开发

保留上游原版镜像，以 `main` 维护个人稳定版本，在 `codex/dev` 开发特色功能，在 `contrib/` 分支准备上游贡献。先区分用户是在咨询方案、开发功能、同步上游还是提交贡献，只执行本次要求的工作。

## 分支与远端约定

| 名称 | 用途 |
| --- | --- |
| `upstream` | 原作者的开源仓库，作为更新来源 |
| `origin` | 用户自己的 fork，作为获准推送后的存放位置 |
| `parent/main` | 本地上游原版镜像，只接收原作者的更新 |
| `main` | 用户自己的稳定版本，包含已验证的个人特色功能 |
| `codex/dev` | 默认的本地开发分支，从 main 创建，开发验证后直接合回 main |
| `dev` | 可选的开发集成分支，仅在用户或项目确实需要时使用 |
| `contrib/<改动描述>` | 从上游原版基线创建，一条分支对应一个向原仓库提交的 PR |

- 默认功能路线：`main → codex/dev → 本地 main`，不要求经过 dev，也不为每次任务另建功能分支。
- 默认同步路线：`upstream/main → parent/main → 本地 main`，不经 codex/dev，避免把未完成的功能带入稳定版。两种路线均在验证通过后才推送或部署。
- 上游贡献路线：`parent/main → contrib/<改动描述> → 推送到自己的 fork → 向原仓库提交 PR`，按下文贡献流程执行。
- `upstream/main` 是远端跟踪引用，`parent/main` 是用户仓库内的镜像分支。上游默认分支是 master 等其他名称时，调整上游引用，不把它与用户的 main 混为一谈。
- 用户明确指定的分支或迁移方案优先。采用本技能不等于授权重命名、删除或覆盖已有分支；旧命名先核对实际角色，迁移时保留已有提交和工作目录。
- 个人功能只交付到用户自己的 main，不合回 parent/main 或原作者仓库。给上游贡献代码需要用户另行提出。

## 开始前核对

在目标仓库读取适用的 `AGENTS.md`，检查 `git status --short --branch`、`git remote -v`、`git branch -vv` 和 `git worktree list`。确认镜像分支、稳定分支、开发分支、远端身份和现有工作目录，简洁说明本次操作目标。

- 按实际 URL 确认远端角色，不只凭 `origin` 或 `upstream` 名称判断。`origin` 可能仍指向原作者仓库；身份不明确时先查仓库信息，仍无法确定再询问。缺少 upstream 时，仅使用已核实的原仓库 URL 添加；不覆盖已有远端。
- 优先复用目标分支所在目录，保护未提交、已暂存及其他任务的改动。无法安全切换或合并时保留现场并说明，不通过强制切换、reset、自动 stash 或清理文件绕过。
- 当前正在 merge、rebase 或 cherry-pick 时，先辨明其归属与状态，不叠加新操作。
- 缺少 parent/main 时，先获取并核实上游默认分支，再从该上游引用创建镜像，不能从含定制提交的 main 创建镜像。缺少 main 时从已核实的原版基线创建；已有 main 则保留其定制历史。
- 已有 codex/dev 时核对任务归属并复用，仅不存在时从 main 创建。已有未完成开发不因同步上游而重置、提前合入或删除。

## 开发个人功能

默认在 codex/dev 实现本次需求，遵守项目实现、检查和本地提交约定，仅包含本次任务改动。验证特色功能及相关原版行为，在已获准交付时直接合入本地 main，再验证整合结果，不额外要求先建立 dev。

- main 已接收上游更新而 codex/dev 仍有开发时，核对后将最新 main 合入 codex/dev，处理兼容性并测试；不通过重建分支丢弃未完成工作。
- 功能交付的 merge 或 squash 方式沿用用户和仓库已有约定；该约定不改变下文“上游同步必须保留祖先关系”的流程。没有其他约定时使用普通 merge。
- 用户或项目确实采用 dev 时再将它作为集成层，并说明实际合并目标，不把它设为所有 fork 项目的必经分支。
- 本地开发与提交不自动授权合入稳定分支、push 或发布；已有合并、推送授权直接沿用，不重复询问。codex/dev 的复用与合入 main 后删除遵守既有约定：完整合入并验证后安全删除，不再归档；保留未完成或尚未合入的工作。

## 同步上游

用户要求同步时执行，不因上游每次有提交就自动升级。通常按准备升级的批次整体合并上游更新，包含功能、修复及其依赖；普通 merge 不会自动挑出“主要功能”。

以下示例仅适用于已核实的 upstream/main、已存在的 parent/main 和本地 main，且相关工作目录可安全操作。按当前项目的真实名称替换，并逐步检查结果：

```sh
git fetch upstream
git switch parent/main
git merge --ff-only upstream/main
git switch main
git merge parent/main
```

- 合并前记录 main tip 和本次上游目标 SHA，查看两边的新增提交、升级说明及配置迁移要求。只更新 parent/main 不代表个人稳定版已经升级。
- parent/main 的 `--ff-only` 失败，或镜像含上游没有的提交时，先检查来源；不在镜像上制造混合历史，不重置或强推来伪装同步成功。main 包含个人提交是正常情况，不能对它强制要求与上游相同。
- 将 parent/main 合入 main 时使用普通 merge，保留上游祖先关系；不使用 squash，不默认 rebase 已发布的 main。即使功能交付采用 squash，上游同步也不套用该流程。
- 默认直接在本地 main 合并，解决冲突并验证后才推送或部署。改动较大或项目需要先验证时，可从 main 建立临时验证分支，合入上游并测试，再用保留祖先关系的 merge 合回 main；不要复用含未完成任务的 codex/dev 来中转。
- 用户指定版本/tag 时，核实其来自上游，再把该版本对应的明确提交合入 main，不夹带 parent/main 中更晚的更新。镜像继续跟随上游默认分支，不回退成指定版本；main 已含更晚版本时说明状态，不把 merge 当作降级。
- 只有明确需要单个修复时才考虑 `cherry-pick`，先检查依赖和是否已经包含；记录原始 SHA。它是例外处理，不替代长期同步流程。

## 向原仓库提交 PR

用户要将功能或修复贡献给原仓库时，使用独立的 `contrib/<改动描述>` 分支。例如 `contrib/fix-rule-validation`、`contrib/add-rules-editor`。每个 PR 使用一条贡献分支；跟进同一 PR 时继续使用原贡献分支，不因追加修改另建分支。

1. 读取原项目的贡献指南、PR 模板及相关检查要求，确定原仓库和目标分支，默认目标为原仓库 main。
2. 获取上游更新，将 parent/main 快进到已核实的 upstream/main，再从 parent/main 创建贡献分支；本次贡献不要求顺带升级个人 main。已有同名分支时先核对是否属于本次贡献，不覆盖。若贡献指南要求目标为 release 等其他分支，则从已更新的对应上游引用创建贡献分支，不改变 parent/main 的镜像角色。
3. 只加入本次贡献的改动。若功能已在个人 main 或 codex/dev 中实现，检查依赖后挑选相关提交或移植必要改动；不要将整个个人分支合入贡献分支，避免夹带其他定制内容。
4. 对照实际上游目标分支检查 PR 的新增提交和完整差异，运行项目要求的相关测试。仅在内容范围和验证结果符合本次贡献时提交 PR。
5. 用户明确要求“向原仓库提交 PR”时，在既有授权范围内将贡献分支推送到自己的 fork，并创建 PR，无需重复询问同一流程。仅咨询或要求本地准备时停在对应范围，不自行推送或创建 PR。
6. 从本地 contrib 分支推送到自己 fork 的同名分支，使用明确 refspec，不向 upstream 直接推送。PR 的 head 选 `自己的 fork:contrib/<改动描述>`，base 选 `原仓库:main` 或贡献指南指定的目标分支；不要误选个人 fork 的 main 作为目标。
7. PR 标题和描述说明具体问题、改动及验证结果，遵循原项目模板。创建后核实来源、目标及 PR 地址，简洁交付；PR 是否被原作者合并属于后续状态，不自动更新或删除个人分支。

贡献流程是“默认仅推送个人 main”的特定例外，不能套用个人功能的 squash 到 main 再推送流程。它不授权将 codex/dev 直接推送或改名发布。

## 冲突与验证

发生冲突时逐文件理解上游变化和个人功能意图，再编辑解决；不批量使用 `ours` / `theirs` 丢弃一侧。技术冲突能明确解决就继续，涉及无法推断的业务取舍时说明具体差异并询问。

解决后检查差异和冲突标记，运行仓库已有的相关测试、类型检查或构建，并验证个人特色功能和受影响的上游行为。用 `git add` 和 `git commit` 完成有冲突的 merge；无冲突的 merge 可能已自动提交。验证失败时继续修复或报告未完成，不将其描述为可发布。若需要撤销，只处理本次发起的合并，先核对工作区并保留需要保留的修改。

## 推送与交付

同步、开发或使用本技能本身不等于授权 push。用户已明确要求推送时沿用授权，不重复确认；核对自己的 fork、目标分支、远端新增提交和 CI/部署影响后再执行。本地 main 已合并但未验证时，不能声称稳定版已可发布。

- 个人版本默认只将已验证的本地 main 推送到用户 fork 的 main；向原仓库提交 PR 时按上面的贡献流程推送 contrib 分支。两种情况均不向 upstream 直接推送。codex/dev 仅本地使用；parent/main 或可选 dev 只有在用户明确要求发布对应分支时才推送。
- 使用明确 refspec，禁用自动跟随标签。例如，确认使用默认名称时推送个人稳定版本：

  ```sh
  git -c push.followTags=false push --no-follow-tags origin refs/heads/main:refs/heads/main
  ```

- 推送前获取目标远端状态，确认没有未经核对的远端提交或其他任务内容。拒绝或并发更新时重新核对，不使用 force push、`--all` 或 `--mirror` 绕过。
- 简洁报告：当前分支、完成的功能或合入的上游版本/SHA、冲突与验证结果、是否已推送及剩余问题。个人交付说明是否已合入本地 main；上游贡献说明 PR 的来源、目标和地址。只完成本地工作时明确写“未推送”。
